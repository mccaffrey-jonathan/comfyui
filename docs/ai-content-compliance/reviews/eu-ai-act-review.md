## 1. Executive summary

The two packs are, for their size, an unusually honest and well-engineered piece of work. The C2PA layer is standards-based and real; the watermark is a defensible classical design with calibrated statistics and a published limitations section; the NOTICE disclaims compliance rather than claiming it. Against the *shape* of what the Code of Practice asks for — **two machine-readable layers, signed metadata plus an imperceptible watermark** — the packs give an operator the raw material for both layers, which is more than most ComfyUI provenance nodes.

But the gap between "produces two layers" and "an Article 50(2) solution that is effective, interoperable, robust and reliable" is wide, and most of it is *not* closed by these packs:

1. **There is no detection facility in the form the Code expects.** Detection of the watermark requires the secret. Everything the packs ship — the `Durable Watermark Detect` node, `python -m durable_watermark detect` — is a *provider-private* tool. The Code's detection commitment is a solution made **available**, in principle free of charge, with an interoperability obligation by **2 February 2027** (a public routing endpoint or a publicly readable signpost in the content) **[secondary]**. The packs provide neither, and the release page nevertheless describes "Detect node and CLI as the detection facility". That is the single largest mismatch between claim and artifact.
2. **The soft binding is non-interoperable and technically off-spec in two ways.** `alg: org.comfyui.ringmark.v1` is not in the C2PA soft-binding algorithm list (verified: 53 entries, not present), so no third-party validator or the Soft Binding Resolution API can dispatch to a decoder; the `value` is a CBOR text string where the CDDL says `bstr` (the packs document this); and the action written is the **deprecated** `c2pa.watermarked` rather than `c2pa.watermarked.bound` (verified in c2pa-rs).
3. **The "durable" claim is not actually implemented.** Durability depends on a manifest registry keyed by the watermark payload. The save node **discards the signed manifest store** (`cc_nodes.py:263`, `signed, _store = ...`) and exposes only the *pre-signing* manifest definition as `manifest_json`. Nothing writes a registry, and nothing resolves one. After a re-encode, an operator following the README has a watermark payload and no way to get back to a credential.
4. **Robustness evidence is far below what the Code's testing commitment implies** **[secondary]**: three images, one key, one payload, no corpus-scale false-positive measurement, no print-and-scan, no regeneration or adversarial attack evaluation (all three are named categories in the Code's robustness language **[secondary]**), no CI regression on robustness, and an internal inconsistency between the README table and the release page's own sweep text about where JPEG payload survival ends.
5. **Provider "enforcement" mode is not an enforcement boundary.** `COMFYUI_WATERMARK_ENFORCE` pins only `secret`, `payload`, `strength` (`keys.py`); it does **not** pin `payload_bits`, `r_min`, `r_max`, `ring_width`, which are inputs to the key-derivation function (`core.py:_kdf`). A tenant who nudges `ring_width` produces a mark the provider's standard detector will not find. Nor does anything force the embed or save node to be present in a graph at all.
6. **Two concrete security defects** that a provider would carry as its own risk: the C2PA save node writes the **unredacted** `extra_pnginfo["workflow"]` into PNG text chunks (`cc_nodes.py:241`) and into the signed manifest when `workflow_in_manifest` is on (`manifest.py`), so a literal secret typed into the Key widget leaks despite the README's claim that it is redacted; and the encrypted private assertion publishes `key_id = sha256(info|passphrase)[:16]` (`crypto_box.py:29,43`) with a single-round HKDF and fixed salt, which is an offline oracle for guessing the passphrase.
7. **Everything deployer-side is absent and correctly labelled out of scope**: no visible deepfake label, no EU AI icon, no multilingual labelling, no text/audio/video.

**Overall:** as *components* for the two marking layers, the packs are a reasonable starting point. As an "Article 50 solution", they are roughly **50-60% of the provider-side machinery**, with the detection facility, the registry, the interoperability signpost, and the evidence base being the missing half — and those are precisely the parts a market-surveillance authority would ask to see.

## 3. Specific technical gaps and risks

Severity is my engineering judgement of the risk to a provider relying on this stack, not a legal grading.

### 3.1 The detection facility does not exist in the form the Code expects — **High**
- The watermark is keyed: `_kdf()` (`core.py:134`) mixes `cfg.secret` into every chip sign, phase, codebook and the noise floor. Without the secret the mark is, by design, statistically invisible.
- Every detection path ships as *code requiring that secret*: `DurableWatermarkDetect` takes a `WATERMARK_KEY` produced by `DurableWatermarkKey` (`wm_nodes.py`), and `cli.py detect` calls `resolve_secret()`.
- The Code's commitment is a detection **solution made available**, in principle free **[secondary]**, plus a routing/signpost interoperability obligation by **2 Feb 2027** **[secondary]**. Source code is not a solution made available; it is a build-your-own kit.
- The release page's regulatory-mapping table states "Detect node and CLI as the detection facility". That is the one place where the documentation overstates what the artifact is, and it should be corrected regardless of anything else in this review.
- Note the asymmetry that saves the packs partly: the **C2PA layer is publicly detectable** without any provider facility. So on an untouched file, third-party detectability holds. The gap bites exactly when the metadata is stripped — the scenario the watermark was added for.

### 3.2 The statistics are better than most, but the quoted p-values are not supported — **Medium**
- `detect()` builds a 96-key empirical null (`core.py:671,706`), takes the **maximum** of each null key's score over the full (scale × rotation × flip × aspect) search (`core.py:743`), then computes `z = (score − mean)/std` and `p = ½·erfc(z/√2)`.
- Taking the max of ~10^5 correlated hypotheses gives a right-skewed extreme-value distribution. Fitting a two-parameter Gaussian to 96 draws and extrapolating to z = 5 (README: "p < 3e-7 per image") extrapolates ~5 standard deviations beyond any observed sample, in the direction where the true distribution has a heavier tail than the Gaussian. The achieved false-positive rate at the default threshold is therefore **unknown and plausibly worse than quoted**.
- Nothing measures FPR on a corpus. "Unmarked images and wrong keys score |z| < 3" (README) is an observation on a handful of images at |z| < 3 — it says nothing useful about the 3e-7 regime.
- A detection service that scans many images at z ≥ 5 will make accusations. For a claim that a file is AI-generated, the tail matters more than the median. Fit a Gumbel to the null maxima, or report a rank-based bound (e.g. "score exceeded all 96 null keys" ⇒ p < 1/97), which is defensible with the data actually collected.
- Related: with no expected payload, the only integrity check on a decoded payload is an **8-bit CRC** (`core.py:crc8`) — ~0.4% of random reads pass. For registry lookup keyed by payload, that is a meaningful mis-attribution rate.

### 3.3 Robustness evidence is not proportionate to the claim — **High**
- Corpus: one real image (ComfyUI's bundled `example.png`), two synthetic images (`tools/bench.py:synth_images`). One secret. One payload. `tools/bench.py` even requires the user to add their own images to the `images` dict.
- Missing entirely, and named in the Code's robustness language **[secondary]**: **print-and-scan**, **screenshot/recapture**, **regeneration** (img2img round-trip through a diffusion model), **removal attacks** (the docs cite UnMarker and MarkNull but run neither), **copying/forgery** (can an attacker transplant a mark onto an unmarked image? For an additive spectral scheme with a fixed key this deserves an explicit test).
- Missing and realistic: social-platform pipelines (a single Instagram/X/WhatsApp round-trip is resize + re-encode + often a slight crop — the README's own worst case, "net <0.65× downscale + JPEG", is that pipeline), AI upscaling, aspect-ratio letterboxing, 10-bit/HDR, alpha channels (the CLI has an ad-hoc RGBA mode expression in `cli.py:_load` that is hard to reason about and likely mis-parses due to Python operator precedence between `and`/`or`).
- **Internal inconsistency:** README/overview table says photo payload survives **JPEG q75** at strength 1.0 and the release gallery shows "JPEG quality 75 — payload verified, z = 10.9"; but the release page's own sweep text says "on the photo the payload survives to about **q90** and presence to about q60 at strength 1.0". These cannot both be the headline. Someone reading the release page gets a materially different picture of JPEG robustness depending on which paragraph they read. Reconcile, and state which image and key the number refers to.
- CI runs `pytest` only; there is **no robustness regression test**, so a change to the ring layout or masking could silently destroy JPEG survival and every test would still pass.

### 3.4 Soft binding: unregistered algorithm, wrong value type, deprecated action, ambiguous payload — **High (interoperability)**
- `alg: org.comfyui.ringmark.v1` (`manifest.py:139-148`) — **verified absent** from the 53-entry [soft-binding algorithm list](https://raw.githubusercontent.com/c2pa-org/softbinding-algorithm-list/main/softbinding-algorithm-list.json). Consequence: a conforming validator cannot know what decoder to run, and the Soft Binding Resolution API cannot route. The soft binding is documentation for the provider, not an interoperable binding.
- `blocks[].value` is a JSON string → CBOR `tstr`; the CDDL says `bstr`. The packs document this and note that today's validators tolerate it. Fine as a known deviation, but it is a deviation, and it is the sort of thing a conformance program would flag.
- The action written is `c2pa.watermarked`, which I **verified is deprecated** in `c2pa-rs` (`actions.rs`, deprecated since 0.91.0) in favour of `c2pa.watermarked.bound` — and "bound" is precisely the semantics here (the payload points at a manifest). `03-c2pa-content-credentials-tooling.md` §3.1 already records this; the code did not follow its own research.
- **Payload/identifier mismatch:** the manifest's unique id is a per-image `uuid4` (`cc_nodes.py:249`); the watermark payload is per-*key* (or per-batch via `payload_override`, which cannot vary within a batch and is ignored under enforce). So for a batch of 4, four manifests share one soft-binding value. Registry lookup by payload cannot disambiguate them.
- **32 bits is small** for an image identifier: ~50% collision probability at ~77k images (birthday bound). A provider that puts a generation-id fragment in a 32-bit payload has an ambiguous registry after a day of traffic. 64 bits exists but the README says it halves the per-bit margin — that trade-off should be measured, not asserted.

### 3.5 "Durable Content Credentials" are claimed but not implemented — **High**
- Durability = watermark payload → registry → manifest. The registry half is absent:
  - `sign_image_bytes()` returns the signed manifest **store bytes**, and `cc_nodes.py:263` discards them (`signed, _store = ...`).
  - The node's `manifest_json` output is the **pre-signing manifest definition** (`manifests.append(manifest)`), not the signed store — so it cannot be served as a recovered credential.
  - Nothing writes a keyed record anywhere; the README tells the operator to "store the `manifest_json` output keyed by `generation_id` / watermark payload" — by hand, from a string output, with no node to do it.
- There is no remote/sidecar manifest support (`set_remote_url`, `set_no_embed`), which is the other standard durability mechanism.
- **Consequence:** the failure mode the whole two-layer design exists to survive — "someone re-encoded the image and the manifest is gone" — leaves the operator with a z-score and a 32-bit number, and no shipped path back to a credential.

### 3.6 Provider enforcement mode is not an enforcement boundary — **High (for the multi-tenant use case the README advertises)**
Three independent bypasses:
1. **Parameters are not pinned.** `enforce_server_settings()` governs only `resolve_secret`, `resolve_payload`, `resolve_strength` (`keys.py`). `payload_bits`, `r_min`, `r_max`, `ring_width` come straight from the node widgets (`wm_nodes.py:70-85`) — and all four feed `_kdf` (`core.py:134-154`). A tenant setting `ring_width = 0.0041` produces a *validly marked* image that the provider's default detector will not find. `payload_bits = 0` additionally removes the identifier.
2. **The node can simply be omitted.** Enforcement conditions how the key node behaves; nothing requires the embed node or the C2PA save node to be in the graph. A tenant workflow ending in the stock `SaveImage` produces an unmarked, unsigned output.
3. **It is not a security boundary.** ComfyUI executes arbitrary custom-node code in-process; under enforce the server secret is materialised into a Python dict (`wm_nodes.py:86-95`) reachable by any node in the graph. If tenants can install or author nodes, the secret is theirs.
**Implication:** a provider who needs a guarantee must enforce *outside* ComfyUI — a post-processing step on the output directory or the serving path — and the README should say so rather than presenting `COMFYUI_WATERMARK_ENFORCE` as the provider answer.

### 3.7 The C2PA save node leaks literal secrets via the workflow metadata — **High (security defect, contradicts documentation)**
- `_redact()` is applied to `prompt` only (`cc_nodes.py:197`). The PNG writer then iterates `extra_pnginfo` and writes every entry **unredacted** (`cc_nodes.py:241`): `for k, v in extra.items(): metadata.add_text(k, json.dumps(v))`. `extra_pnginfo["workflow"]` is the front-end graph, which contains `widgets_values` — including a literal secret typed into the Key node's `secret` widget.
- `redact_prompt()` (`keys.py`) only understands the API-format prompt (`{id: {class_type, inputs}}`); it does not touch the front-end workflow format (`{nodes: [{type, widgets_values}]}`).
- With `workflow_in_manifest = true`, the same unredacted workflow is placed in `org.comfyui.workflow` **inside the signed manifest** (`manifest.py`, `include_workflow`) — i.e. a literal secret becomes a permanently signed, publicly readable part of the credential.
- The durable-watermark README states: "the C2PA save node redacts them from the metadata it writes." **That is currently inaccurate**, and it is the claim that makes a user comfortable typing a literal secret.
- Secondary: `encrypt_prompt` stores the **unredacted** `prompt` (`cc_nodes.py:216`, `priv["prompt"] = prompt`, not `red_prompt`) — encrypted, so lower risk, but combined with §3.8 it is not a strong protection.

### 3.8 Key material is derived and published in ways that enable offline guessing — **Medium-High**
- `WatermarkConfig.key_fingerprint()` = first 8 bytes of a **single SHA-256** over `domain | secret | params | "fingerprint"` (`core.py:129-154`), and it is **published in the soft binding** (`manifest.py:139`) and in `org.comfyui.watermark`. If the secret is a human-chosen passphrase, an attacker with one published image can brute-force it offline at SHA-256 speed; with the secret, the mark can be removed *and forged onto other images*.
- `crypto_box.key_id()` = `sha256(_INFO | passphrase)[:16]`, written into the manifest (`crypto_box.py:29,43`). This is a direct **passphrase-confirmation oracle** — an attacker can verify guesses without touching the ciphertext. Key derivation itself is HKDF-SHA256 with a **fixed salt** and no work factor (`crypto_box.py:19,26`); HKDF is a key-*expansion* function, not a password hash.
- Fixes are cheap: derive the fingerprint/key-id from a random per-key salt stored server-side (or from the public parameters only, not the secret); use Argon2id/scrypt for passphrase-derived keys; and prefer high-entropy random secrets, which the docs should mandate rather than merely suggest (`config/watermark.json.example` shows a *payload* string, not a secret-generation recipe).

### 3.9 C2PA manifest content issues — **Medium**
- **Self-asserted legal claims inside a signed manifest.** `org.comfyui.generation.claims.regulatory_notes` embeds the strings "EU AI Act Art. 50(2) machine-readable marking" and "California B&P Code 22757.3 latent disclosure fields …" (`manifest.py:106-112`), cryptographically signed by the provider. This is a signed statement that the asset satisfies named legal provisions — exactly what the NOTICE spends a paragraph disclaiming. It adds no machine value and creates a representation a regulator or counterparty can quote back. **Remove it** or reduce it to a neutral schema pointer.
- `allActionsIncluded: true` (`manifest.py:121`) is asserted unconditionally, while the node knows nothing about upstream ComfyUI operations (upscale, composite, inpaint) and does not emit a `c2pa.opened` action for the `parent_image` ingredient it adds. The claim is probably false in most img2img graphs.
- `digitalSourceType` is not adjusted when `parent_image` is connected (A8).
- `provider_name` defaults to empty (`cc_nodes.py`), in which case `claim_generator_info` carries no provider and `org.comfyui.generation.provider` is dropped by the `None` filter — silently producing a manifest without the party responsible for the content. There is no warning.
- Test-certificate runs produce `signingCredential.untrusted`; the node saves happily with no warning on the output. A provider that forgets to swap certificates ships thousands of untrusted assets.
- No `c2pa.metadata` / `cawg.metadata` / XMP `Iptc4xmpExt:DigitalSourceType`, so tools reading XMP rather than C2PA see no AI indication at all.
- `verify.py` reports failures from `validation_results.activeManifest.failure` only — ingredient-level failures are not surfaced in the summary.

### 3.10 "Must be the last writer" is a real operational hazard — **Medium**
- Any node that re-encodes after `C2PASaveImage` destroys the manifest; so does any editor, and so does essentially every social platform. The docs say this clearly (README Limitations, release page "Known limits").
- What is missing is any *defence*: no post-save verification step, no warning if another output node exists downstream, no sidecar/remote manifest fallback, and no registry (§3.5) to recover from. The watermark survives, but only the provider can read it (§3.1). The net effect is that the common case — an image that has been through one platform — has **no publicly detectable marking left**.

### 3.11 Coverage gaps a ComfyUI operator will actually hit — **Medium**
- **Video and audio**: ComfyUI generates both; neither pack marks either; nothing warns. C2PA supports MP4/MOV/MP3/WAV.
- **Other save/preview paths**: `PreviewImage`, `SaveImage`, `SaveAnimatedWEBP`, API `/view` outputs and any custom saver bypass both layers entirely.
- **Batch semantics**: one payload per batch vs per-image manifests (§3.4).
- **Small images**: below ~256-300px the default ring width does not fit; thumbnails are effectively unmarked at the watermark layer (documented).
- **Alpha/16-bit**: the save node flattens through `np.clip(255.0*…).astype(np.uint8)`; the CLI's RGBA detection expression is suspicious.
- **Multilingual / accessible labelling**: not covered anywhere (deployer duty, but the packs are the natural place for a helper).

### 3.12 Provider vs deployer duties a ComfyUI operator still carries — **informational**
A single operator is usually **both**:
- As **provider** (places a generative system on the market — including an open-source one, G1/G2): 50(2) marking + detectability, the Code's detection and interoperability commitments, robustness testing and documentation, security of the marking, and (if a signatory) reporting.
- As **deployer** (publishes or uses the outputs): 50(4) deepfake disclosure with the EU AI icon or equivalent, 50(5) timing at first exposure for every new viewer, labels that persist down the distribution chain, internal processes and staff training, correction of missing labels, cooperation with authorities. **None of this is in the packs.**

### 4.1 MUST — for the node packs (correctness, security, or a claim that is currently unsupported)

| ID | Recommendation | Concrete implementation |
|---|---|---|
| **R-M1** | **Stop describing the Detect node and CLI as "the detection facility"** in the README and the release page | Replace with: "a provider-private detector; the Code's detection commitment requires a service you operate — see [link]". | **R-M2** | **Ship a detection service, not just a detector** | Add a `tools/detect_server.py`: FastAPI/Flask, `POST /detect` (multipart image) → `{ai_generated, layer: c2pa\|watermark, z, p_bound, payload, generation_id?, manifest?}`. | **R-M8** | **Pin *all* key-schedule parameters under enforce (§3.6)** | Extend `keys.resolve()` to return enforced `payload_bits`, `r_min`, `r_max`, `ring_width`, `perceptual_mask`, `noise_floor`, and have `DurableWatermarkKey` ignore the widgets when enforced (log once). | **R-M9** | **Warn loudly on untrusted signing and missing timestamp/provider** | At save time (not just signer load): log a warning per run when `signer["is_test"]`, when the TSA produced no timestamp, and when `provider_name` is empty. Add an `on_untrusted` mode (`warn` / `fail`) so a production deployment can make it an error. |
| **R-M10** | **Correct the JPEG robustness inconsistency (§3.3)** and state the test conditions | Reconcile README table / overview / release-page sweep text; state image, key, payload bits and strength next to every number. |

### 4.2 SHOULD — for the node packs

| ID | Recommendation | Concrete implementation |
|---|---|---|
| **R-S1** | **Implement the registry half of "durable" (§3.5)** | Keep the signed store from `sign_image_bytes` and add a `C2PA Manifest Registry Write` node (or a `registry_dir` input) writing `{payload_hex}/{generation_id}.c2pa` plus an index row `{payload, generation_id, key_fingerprint, sha256, created, manifest_path}`. Add a resolver in the detection service (R-M2) and, optionally, a C2PA Soft Binding Resolution API shim. |
| **R-S2** | **Make the payload per-image and wider** | Derive the payload from the per-image `generation_id` by default (`payload = first N bits of SHA-256(generation_id)`), which requires the embed node to know the id — simplest fix: let `DurableWatermarkEmbed` mint the id and hand it to the save node via `watermark_record`, replacing the save node's `uuid4`. Default to 48-64 bits and publish the margin cost. |
| **R-S3** | **Support key sets and key rotation** | Accept a list of keys in the detect node/CLI/service; add a `key_version` field to the record and (if bits allow) to the payload; document rotation cadence and the retention of old keys for detection. Cache the 96-key null schedule across keys to avoid the linear slowdown. |
| **R-S4** | **Report defensible statistics (§3.2)** | Replace the Gaussian p-value with a Gumbel fit to the 96 null maxima or a rank bound (`p ≤ 1/(n_null+1)` when the score exceeds all nulls); report both. Publish a corpus FPR study (≥10k unmarked images across content types) and state the achieved FPR at the default threshold. Strengthen the payload check beyond CRC-8 when used for registry lookup. |
| **R-S5** | **Build a real robustness harness and put it in CI** | Extend `tools/bench.py` into a dataset runner (50-200 images spanning photo/illustration/flat/text-heavy/small), add print-and-scan simulation, screenshot/recapture, a social-pipeline composite, an img2img regeneration round-trip and at least one published removal attack; emit a versioned JSON report; add a CI job asserting thresholds on a small fixed subset so regressions fail the build. |
| **R-S6** | **Add an interoperability signpost (Code, by 2 Feb 2027) (§C6)** | Either register the algorithm (R-M5b) or add an optional **second, unkeyed** watermark layer whose only job is to say "ask `https://detect.example.com`": e.g. TrustMark signpost mode (MIT, already in the registry) chained before the C2PA save node, with both marks recorded as soft bindings. The docs already recommend TrustMark layering — make it a supported node rather than a suggestion. |
| **R-S7** | **Write XMP/IPTC alongside C2PA** | Add `Iptc4xmpExt:DigitalSourceType` to XMP (and, for operators serving China, the TC260 fields) so non-C2PA tooling sees the AI indication; consider a `cawg.metadata` assertion for `dc:creator`/`xmp:CreatorTool`. |
| **R-S8** | **Close the "other save paths" hole** | Document explicitly that `SaveImage`/`PreviewImage`/video savers bypass both layers; optionally ship a server-side hook or a linter script that fails a workflow lacking the embed+save pair. |
| **R-S9** | **Provide deployer-side helpers even though the duty is the operator's** | A `Burn-in AI Label` node (EU AI icon per the Commission's placement specifications, configurable corner/opacity/locale, plus a "generated"/"manipulated" variant), so an operator producing deepfake content is one node away from a 50(4) label. | **R-S10** | **Document the provider/deployer split and the FOSS non-exemption in the READMEs** | A short "Who is on the hook" box: whoever places the system on the market is the provider; open source is not exempt; you are usually also the deployer; here is what these packs do and do not cover. |

### 4.3 COULD — for the node packs

- **R-C1** Logging layer (Recital 133): optional append-only JSONL of `{generation_id, payload, key_fingerprint, sha256, model, created}` per output, with retention guidance — feeds R-S1 and gives an audit trail.
- **R-C2** Perceptual fingerprint (e.g. ISCC `io.iscc.v0`, already in the registry) as a third, unkeyed recovery path that works without the secret.
- **R-C3** HSM/KMS signer node, so production keys never sit in a PEM on disk (currently README-only via `Signer.from_callback`).
- **R-C4** Sidecar / remote manifest support (`set_no_embed`, `set_remote_url`) for formats and pipelines that strip embedded manifests.
- **R-C5** Video/audio marking (C2PA SDK already supports the containers; watermarking video is a larger project).
- **R-C6** A `C2PA Verify After Save` node that re-reads the written file and fails the run if the manifest is absent or untrusted.
- **R-C7** Publish a machine-readable "marking solution card" (JSON) describing layers, algorithm ids, versions, evaluation results and the detection endpoint — the artefact a signatory would attach to a report.

### 4.4 For an operator deploying these packs (independent of pack changes)

**Must:**
1. Decide, in writing, whether you are a **provider** (placing a generative system on the market — open source does not exempt you **[secondary]**), a **deployer**, or both; date it and keep it.
2. Use a **production C2PA certificate** from a CA on the C2PA Trust List; never ship the test chain; verify a sample of outputs shows `Trusted` in a public verifier; keep the TSA enabled and monitor that `signature_info.time` is actually populated.
3. Generate a **high-entropy random** watermark secret; store it in a secret manager; never in a workflow widget; assume anything typed into a widget is public.
4. **Enforce marking outside ComfyUI** — a post-processing step on the serving path or output directory — because in-graph enforcement is bypassable (§3.6).
5. Stand up a **detection endpoint** (R-M2) and publish its URL; plan the interoperability solution for **2 Feb 2027** **[secondary]**.
6. Operate a **manifest registry** keyed by watermark payload and generation id, and keep the signed store bytes (§3.5).
7. Apply **visible disclosure for deepfake outputs** (EU AI icon or equivalent) at the surface where people see them, at first exposure (Art. 50(4), 50(5)).
8. Mark **non-image outputs** (video, audio, text) by other means, or do not produce them.

**Should:** run a pre-market robustness evaluation and repeat it on a schedule, with red-teaming; keep a dated evaluation report; document key management and rotation; monitor the legacy-system deadline of **2 Dec 2026** if your system predates 2 Aug 2026; check whether signing the Code of Practice suits you and, if so, what you must report; track CEN-CENELEC JTC 21 harmonised standards; re-read the Code's operative text (I could not).

## 5. What a provider still has to do outside these nodes — checklist

- [ ] **Legal characterisation**: provider and/or deployer, per output type; record the reasoning. Open-source release is not an exemption **[secondary]**.
- [ ] **Guarantee of marking** at the system level (not workflow level) for every output that leaves the system.
- [ ] **Production signing identity**: C2PA-Trust-List certificate, key in an HSM/KMS, rotation and revocation procedure, timestamping verified.
- [ ] **Watermark key management**: high-entropy secrets, storage, rotation schedule, retention of retired keys for detection, incident procedure if a secret leaks (a leaked secret means forgeable *and* removable marks).
- [ ] **Detection solution made available**, in principle free of charge **[secondary]**; documented; rate-limited; monitored.
- [ ] **Interoperability of detection by 2 Feb 2027** **[secondary]**: a public routing point or a publicly readable signpost in the content.
- [ ] **Manifest registry / soft-binding resolution** so a stripped file can be reconnected to its credential.
- [ ] **Robustness and security testing**: pre-market and periodic, covering compression, cropping, format conversion, print-and-scan, and adversarial copying/removal/regeneration **[secondary]**; independent review or red-teaming where warranted; dated reports retained.
- [ ] **Deployer-side labelling**: EU AI icon or equivalent for deepfakes, visible at first exposure for each viewer, persisting through the distribution chain; generated-vs-manipulated indication; audio disclaimers where visual labelling is impossible **[secondary]**.
- [ ] **Coverage of other modalities**: video, audio, text (>~200 tokens for the Code's text watermark measure **[secondary]**).
- [ ] **Internal processes**: staff training, a route to correct missing or wrong labels, cooperation with market-surveillance authorities, complaint handling.
- [ ] **Documentation package**: which marking techniques, which versions, which algorithm identifiers, evaluation evidence, detection endpoint, key-management summary — the file you hand an authority.
- [ ] **Code of Practice decision**: sign or not; if signed, the reporting obligations that follow **[secondary]**.
- [ ] **Deadlines tracked**: 2 Aug 2026 (in force), **2 Dec 2026** (legacy-system marking grace ends), **2 Feb 2027** (detection interoperability **[secondary]**); plus non-EU regimes if you serve them (California SB 942/AB 853 operative 2 Aug 2026, China GB 45438-2025, Korea, India).
- [ ] **Re-verification of this review's [secondary] claims** against the operative text of the Code of Practice and Guidelines C(2026) 5054, which I could not reach.
